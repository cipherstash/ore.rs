**vitaminc is the front door.** ore-rs no longer has a typed API of its own: the typed
way in is `vitaminc-ore`'s `OrderSpace` chain, and ore-rs implements its `OrderScheme`
and `OrderQuery` traits. The design and its reasons are in
`docs/plans/2026-10-19-ore-0-10-vitaminc-front-door.md`. **No stored ciphertext changes:**
the Bit6, chained and legacy wire formats are the frozen 0.9.0 formats, and the
compatibility vectors now go in through the public path, so they pin that too. Three
exceptions sit in the encodings, not the formats: an `f32`, a sub-microsecond
`DateTime<Utc>`, and a string stored with the chained scheme's `encrypt_str` (see below).
The
`vitaminc` feature of 0.9 was unreleased, so nothing stored depends on the adapters it
had.

### Changed

- **`vitaminc` is a dependency, not a feature.** `BlockOre`, at the crate root, is the one
  scheme (there is no `vitaminc` module, since every path goes through vitaminc):
  it implements `OrderScheme` and `OrderQuery` for every target, and routes a space to
  the Bit6 engine (up to ten bytes: `I16` to `U64`, `F64`, `Date`) or the chained engine
  (the rest, text and bytes included) when the space is opened. Text is padded under
  `BlockOre::with_text_padding`, bytes are not, and both are refused past
  `BlockOre::with_max_bytes`. `compare` and `compare_query` dispatch on the wire header.
  A space refuses a plaintext of another target (`OreError::TargetMismatch`, new), which
  only a direct `encrypt_plaintext` or `encrypt_query` call can hand it.
- **The schemes take sealed plaintexts only.** `OreScheme`, sealed, replaces the
  `OreCipher` and `OreEncrypt` traits: `encrypt_plaintext` and `encrypt_query_plaintext`
  over `vitaminc_ore::OrderPlaintext`, giving `Term` and `Query` (serialised bytes), and
  `compare_raw_slices` and `compare_left_to_full` over bytes on all three schemes. The
  legacy scheme gains the query comparator; Bit6 gains it from #120.
- **Keys and salts are vitaminc's types.** `init(Protected<[u8; 16]>)`,
  `init_with_salt(key, &Context)`, `Options::with_salt(&Context)`; the legacy scheme's
  `init(Protected<[u8; 16]>, Protected<[u8; 16]>)`. A 0.9 salt of raw bytes is
  `Context::from_encoded(bytes)` and keys the same ciphertexts.
- **One type per scheme.** The `R: Rng + SeedableRng` generic and the `*ChaCha20`
  aliases are gone: `OreAes128Bit6`, `OreAes128Bit6Chained` and `OreAes128` are concrete,
  draw nonces from a `vitaminc_random::SafeRand` behind a mutex, and are `Send + Sync`.
  `init_seeded`, behind the `test-support` feature, pins a nonce stream for tests.
- **Timestamps are truncated to microseconds.** vitaminc's `Timestamp` target keeps the
  0.9 `DateTime<Utc>` layout (sign-flipped seconds, then the sub-second nanoseconds) but
  rounds the nanoseconds down to whole microseconds. A 0.9 legacy ciphertext of a
  timestamp with a non-zero sub-microsecond part, or of a leap second, has other bytes
  from a 0.10 term for the same instant: they do not compare equal. Timestamps on whole
  microseconds, which is everything PostgreSQL stores, are unchanged.
- **Strings go in through vitaminc's `Text` encoding.** It puts a marker byte before the
  text and folds case and accents, and the marker can move a string into the next padding
  bucket, so a 0.10 term or query of a string encrypts other bytes than 0.9's
  `OreAes128Bit6Chained::encrypt_str` did for it, and the two compare as noise.
  Re-encrypt stored chained strings through a `Text` space. Fixed-width values on the
  chained scheme (`u128`, `i128`) are unchanged.
- **Ceilings and fixed lengths are non-zero.** `Options::with_max_bytes`,
  `BlockOre::with_max_bytes` and their getters take and give a `NonZeroUsize`, and
  `DEFAULT_MAX_STR_BYTES` is one; `Padding::Fixed { max_bytes }` is a `NonZeroU16`. A
  zero, which no value could fit, no longer compiles, and a chained ciphertext whose
  header names `Fixed { max_bytes: 0 }` (which only the empty string could make) no
  longer parses.
- **`Term` is not `PartialEq`.** A term carries a random nonce, so `==` on two terms of
  one value was `false`; compare through the scheme. `Query`, which is deterministic,
  keeps it.
- **vitaminc-ore's `chrono`, `rust_decimal` and `uuid` features are the dependant's.**
  ore-rs no longer turns them on; a dependant that encrypts those types turns them on in
  its own `vitaminc-ore` dependency.
- **MSRV is 1.88**, vitaminc's floor.
- `OreError::RandError` is `OreError::Random(vitaminc_random::RandomError)`, and
  `OreError::VariableLength` is new: text or bytes on a fixed-width scheme.
- The legacy scheme's `compare_raw_slices` refuses an input of more than fifteen
  blocks (`MAX_BLOCKS`), as its typed path always has; the scheme never produced one,
  so no stored ciphertext is affected.

### Removed

- The `OreEncrypt` trait and every per-type implementation, `encrypt_str`,
  `encrypt_left_str`, `encrypt_fixed` and `encrypt_left_fixed`. Typed values enter through
  vitaminc's `FitsIn` table; strings stored with `encrypt_str` need re-encrypting (see
  Changed).
- `CipherText<S, N>`, `Left<S, N>`, `Right<S, N>`, `ChainedCipherText<N>`, `ChainedLeft<N>`,
  `VarCipherText`, `VarLeft`, `OreOutput`, `WireHeader`, `CipherTextBlock`, `ParseError`
  and `PlainText<N>` from the public API. A term's plaintext type lives on vitaminc's
  `OrderTerm<_, T>` (closes #127).
- The per-block types `scheme::bit2::block_types` (`LeftBlock16`, `RightBlock32`) and
  `scheme::bit2_w6::block_types` (`RightBlock8`), and their re-exports from
  `scheme::bit2` and `scheme::bit2_w6`: the only trait they implemented is crate-private
  now.
- The `chrono` and `decimal` features and the `orderable-bytes` dependency: vitaminc owns
  the encodings, ported byte for byte except for timestamps (below).
- The 8-bit plaintext types (`bool`, `u8`, `i8`), which vitaminc has no target for: 256
  values make an order term a frequency table.
- `char`, which vitaminc has no target for. A 0.9 `char` ciphertext (legacy or Bit6)
  still parses and compares against another, but 0.10 cannot make a term to query it.
- `f32` as a type of its own. vitaminc widens an `f32` exactly to its `F64` target, so a
  new term encrypts eight bytes where a 0.9 `f32` ciphertext (legacy or Bit6) encrypted four, and
  the two never compare. Re-encrypt stored `f32` data as `F64`.
- The `vitaminc` module: `BlockOre`, `BlockOreSpace` and `ORE_KEY` are at the crate root.
  `vitaminc::Bit6BlockOre`, `vitaminc::ChainedBlockOre`, the legacy adapter and
  `vitaminc::VARIABLE_WIDTH_MARKER` are gone (vitaminc's encodings carry the marker now).

## [0.9.0] - 2026-10-19

The first release of the ORE v2 schemes. **The Bit6 (`scheme::bit2_w6`) and chained
(`scheme::chained`) wire formats are frozen from this release:** the compatibility vectors
in `tests/` pin their bytes, and a change to them would break stored ciphertexts. Store
them from 0.9.0 on. Ciphertexts made by 0.9.0-rc.1 do not carry over: both schemes are
re-keyed, and the chained header has grown (see Changed). Legacy `OreAes128` ciphertexts
are byte-for-byte unchanged.

### Highlights

These are the changes since 0.8.4. The [0.9.0-rc.1](#090-rc1---2026-10-12) notes below
describe the two new schemes in detail.

- **`OreAes128Bit6` (`scheme::bit2_w6`) for new fixed-width data.** Against the legacy
  scheme, for a `u64` (Apple M1 Max, hardware AES, measured for this release):
  - **About twice as fast to encrypt:** 11.3 µs against 21.8 µs for a full ciphertext, and
    8.3 µs against 15.0 µs for a left (query) ciphertext. Each 6-bit block costs 64
    random-oracle evaluations instead of 256.
  - **28% less to store:** a full ciphertext is 295 bytes against 408. A block's right half
    is 8 bytes instead of 32, so the right half of a `u64` is 104 bytes against 272. A left
    ciphertext is larger, 191 bytes against 136: it carries a header and 11 blocks rather
    than 8.
  - **Less leakage:** no zero-run leakage, since each PRP seed binds the block index and the
    block count.
- **The chained scheme (`scheme::chained`) for strings and other variable-length data.**
  Strings are padded with NULs to a length bucket by default (powers of two with a 16-byte
  floor), so a ciphertext reveals the bucket, not the exact length. A cipher refuses
  strings past a ceiling (1024 bytes by default). `u128` and `i128` are encrypted here too.
- **One key and an optional salt** key both v2 schemes: `init(key)`,
  `init_with_salt(key, salt)`.
- **vitaminc.** The `vitaminc` feature implements `vitaminc-ore`'s `OrderScheme` (vitaminc
  0.6.1, Rust 1.88).
- **No panics in library code.** Errors are returned; internal length contracts are types.
- **Faster key setup on hardware AES.** Every cipher is the encrypt-only `Aes128Enc`, so
  the legacy comparator, which keys a cipher per comparison, is about 20% faster.

### Upgrading from 0.8

- `OreCipher::init(k1, k2)` is no longer a trait method. Call the scheme's own
  constructor: `OreAes128ChaCha20::init(&k1, &k2)`.
- `u128` and `i128` no longer encrypt with `OreAes128` (every call panicked). Use the
  chained scheme.
- `RightBlock32::set_bit` takes a `u8`.
- On aarch64, hardware AES needs `--cfg aes_armv8` in your build configuration (see the
  README); without it AES falls back to software.

### Added

- `OreAes128Bit6Chained::init_with(key, Options)`: `Options` carries the string `Padding`
  policy (#110) and `max_bytes`, the longest string the cipher encrypts (default 1024
  bytes, `DEFAULT_MAX_STR_BYTES`). A longer string returns `OreError::TooLong`. Ciphertext
  size and encryption time grow with the padded length and the string is caller-supplied,
  so a ceiling bounds what one input can cost; it also bounds the number of length buckets
  the ciphertexts can show. `init_with_padding` is replaced by `init_with`.
- The v2 schemes (`OreAes128Bit6`, `OreAes128Bit6Chained`) are keyed from **one 16-byte key**
  and an optional **salt**: `init(key)` and `init_with_salt(key, salt)`; on the chained scheme
  the salt is also an `Options` field (`Options::with_salt`), beside the padding policy and
  ceiling, for `init_with(key, options)`. Derivation is
  `k_root = AES_key(root label)`, `k_salt = CMAC_{k_root}(salt)`, then one `AES_{k_salt}(label)`
  per PRF; the caller's key is evaluated on nothing but the root label. Ciphertexts under
  different salts share no key material. Closes #89.
- `u128` and `i128` can be encrypted, on the chained scheme (`scheme::chained`): `OreEncrypt`
  impls producing `ChainedCipherText<22>` / `ChainedLeft<22>`, whose typed parsers and
  comparators accept only that block count, plus `encrypt_fixed` / `encrypt_left_fixed` for
  any `FixedOrderableBytes` type and `VarLeft::from_slice`. Wire vectors are pinned in
  `tests/compat_chained_vectors.rs` (#105).
- `scheme::bit2::MAX_BLOCKS` (15): the most bytes the legacy scheme takes.
- The chained scheme's string encryptors pad a string with NUL bytes to a length bucket
  (`Padding`): `PowerOfTwo { min_bytes: 16 }` by default, `Fixed { max_bytes }`, or `None`.
  A 3-byte policy tag follows the common header (7 bytes in all), and the comparators
  return `None` for two ciphertexts under different policies. A string that ends in NUL is
  refused (`OreError::TrailingNul`), since it would encrypt like the string without it
  (#104, #110).
- The `vitaminc` feature: `vitaminc::{Bit6BlockOre, ChainedBlockOre, BlockOre}` implement
  `vitaminc-ore`'s `OrderScheme` and `OrderKeyInit`. The v2 schemes bind vitaminc's salt
  with `init_with_salt`, under an ORE key derived once from the scheme key. The chained
  scheme takes text and bytes behind `VARIABLE_WIDTH_MARKER`, up to 1023 bytes. Off by
  default, needs vitaminc 0.6.1 and Rust 1.88 (#115).
- docs.rs builds with the `chrono`, `decimal` and `vitaminc` features.

### Changed

- **Breaking:** `OreCipher::init(k1, k2)` is gone from the trait. Each scheme has its own
  constructor: `OreAes128::init(k1, k2)` (unchanged signature, inherent), and
  `OreAes128Bit6::init(key)` / `OreAes128Bit6Chained::init(key)` plus `init_with_salt`.
  Replace `let ore: OreAes128ChaCha20 = OreCipher::init(&k1, &k2)` with
  `OreAes128ChaCha20::init(&k1, &k2)`, and Bit6's two keys with one.
- **v2 wire, breaking for rc.1 ciphertexts:** every Bit6 and chained ciphertext is re-keyed
  by the new derivation, and the chained header carries the padding tag. The Bit6 and chained vectors are re-pinned; the legacy
  vectors are unchanged. The wire format itself (header, layout) is unchanged.
- **Breaking for rc.1:** the chained scheme's raw-symbol encryptors (`encrypt_var`,
  `encrypt_left_var`) are no longer public. Strings are its public plaintext, with
  `encrypt_fixed` for fixed-length types (#110).
- `Padding` and `OreError` are `#[non_exhaustive]`.
- CI builds and tests on Rust 1.88, the `vitaminc` feature's floor.
- `OreEncrypt<T>` no longer requires `T: OreCipher`, so the chained scheme (which is not an
  `OreCipher`) can implement it. Existing impls and callers are unaffected.
- Every `OreEncrypt` impl macro now emits a round-trip and ordering test for the type it
  implements, so a type can't be declared supported without being exercised (#105).
- Library code no longer panics through `assert!`, `debug_assert!`, `unwrap` or `expect`.
  Length contracts between internal buffers are carried by array types, so a mismatch is a
  compile error, and clippy's panic lints are denied outside tests (CI also rejects runtime
  assertions, which clippy cannot lint). **Breaking:** `RightBlock32::set_bit` takes the bit
  as a `u8`, which names exactly its 256 bits.

### Performance

- Every AES cipher is the encrypt-only `Aes128Enc`. On the hardware backends (AES-NI,
  ARMv8 with `aes_armv8`) key setup no longer builds a decryption schedule, so the legacy
  comparator is about 20% faster (`compare-8`: 233 → 187 ns on an Apple M4) and legacy
  encryption 3–6% faster. Bit6 and chained are within ±1%. The software backend is
  unchanged (#109).

### Removed

- **Breaking:** `OreEncrypt<OreAes128>` for `u128` and `i128`. Every call panicked (see
  Fixed), and code that called `1u128.encrypt(&legacy_ore)` no longer compiles. Encrypt
  128-bit integers with the chained scheme (`scheme::chained`) instead (#105).

### Fixed

- `OreAes128` panicked with an index out of bounds on any 16-byte plaintext, which is what
  the `u128`/`i128` impls on that scheme had always done (#105). Those impls are removed (see
  Removed): the legacy scheme cannot take 16 bytes, and the impl macro now rejects such a type
  at compile time. Encrypting a `PlainText<N>` with `N > 15` directly returns
  `OreError::TooManyBlocks` instead of panicking.
- `OreAes128Bit6` panicked on a `PlainText<N>` with `N > 14` (`MAX_BLOCKS`) through
  `OreCipher::encrypt` / `encrypt_left`; it now returns `OreError::TooManyBlocks`, as the legacy
  scheme does.

## [0.9.0-rc.1] - 2026-10-12

Pre-release for testing with external projects. The Bit6 (`scheme::bit2_w6`) and chained
wire formats are not frozen yet: do not store their ciphertexts until 0.9.0.

### Highlights

**New: `OreAes128Bit6` (`scheme::bit2_w6`), a 6-bit block scheme, recommended for new data.**

- **Smaller and faster.** Plaintexts are split into 6-bit blocks, so each block costs 64
  random-oracle evaluations instead of 256 and stores an 8-byte right block instead of 32.
  A `u64` ciphertext is 295 bytes (legacy: 408). Encrypting a `u64` measured 8.6 µs
  against 25.1 µs for the legacy scheme, both with hardware AES on an Apple M1 Max
  (`docs/benchmarks/2026-06-13-bit6-prp-results.md`).
- **Less leakage than the legacy scheme.** PRP seeds bind the block index and the block
  count, so a ciphertext no longer reveals its runs of zero bytes (for an integer, its
  order of magnitude). A comparison reveals the order and the first differing 6-bit block.
- **Key separation.** PRF keys are derived from the caller's keys under scheme-specific
  labels, so using the same keys for both schemes can't expose Bit6 masking keys
  through legacy ciphertexts.
- **v2 wire format.** A 4-byte header carries the format version, scheme id and block
  count. Parsers and the raw comparator reject bad headers, lengths and out-of-domain
  symbols instead of panicking.
- **Side-channel hardening.** The permutation is built with no secret-dependent memory
  addresses, table reads and the comparator are constant-time scans, and the stack an
  encryption used is zeroed afterwards so PRP seeds and tables don't linger in memory.
- **Coverage.** `bool`, integers up to 64 bits, `char`, `f32` and `f64` (at most 14
  blocks). `Decimal` stays on `OreAes128`. `u128`/`i128` are supported by neither scheme
  (#105).

**New: chained-prefix scheme (`scheme::chained`) for variable-length data and strings.**
Per-block secrets come from a CMAC accumulator over the prefix, so plaintexts aren't
limited to 14 blocks. Every ciphertext reveals the exact plaintext length; padding is
tracked in #104.

**Legacy `OreAes128`.** Ciphertexts are byte-for-byte unchanged (pinned by compatibility
vectors). Encryption is much faster (hardware AES on aarch64 and bulk encoding: a `u64`
went from 381 µs to 25.1 µs in the same benchmarks), the comparator is hardened, and
malformed input is refused. The README now documents the scheme's zero-run leakage.

**Hardware AES on ARM.** On aarch64, including Apple Silicon, the `aes` crate uses
hardware AES only when built with `--cfg aes_armv8`. Downstream projects must set it in
their own build configuration (see the README); without it, AES falls back to software
and is far slower.
