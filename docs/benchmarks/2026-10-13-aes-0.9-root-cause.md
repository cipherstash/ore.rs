# Why `aes` 0.9 is slower on aarch64

Follow-up to `2026-10-12-aes-0.9-results.md`, which measured `aes` 0.9.3
against 0.8.4 but did not find the cause. This note bisects the slowdown
to two separate upstream changes and measures a mitigation on the ore-rs side.

**Result:**

1. **Block encryption (0.9.3 only).** The 2–2.5x per-call slowdown came in
   with block-ciphers #580 (9b8b0c9), released in `aes` 0.9.3. Upstream
   fixed it in #598 (a7136b4, merged 2026-09-18), which is not yet released.
   `aes` 0.9.2 and upstream master are as fast as 0.8.4 with `aes_armv8`, or
   faster.
2. **Legacy comparisons (every 0.9 release, with the `zeroize` feature).**
   Since 0.9.0, dropping an `Aes128` wipes the whole struct one byte at a
   time. The legacy comparator builds and drops an `Aes128` on every call,
   so comparisons stay 21–62% slower even on upstream master. Upstream has
   acknowledged this (RustCrypto/utils#1504) but has no fix. Using
   `Aes128Enc` in ore-rs halves the cost.

## Method

- Apple M4, macOS, rustc 1.89.0 for every build. Release profile,
  `codegen-units = 1`.
- **Microbenchmark:** a scratch crate with a hand-rolled timer (median of
  21 samples), built against each `aes` version from crates.io or a
  block-ciphers checkout. Its shapes:
  - one block
  - a dependent chain of 16 blocks (latency-bound, like CMAC)
  - 32 and 256 blocks
  - key schedule
  - new key + 32 blocks
  - new key + one block + drop (the legacy compare shape)
- **ore-rs benches:** the same five criterion benches as before
  (`oreaes128`, `bit6`, `chained`, `decimal`, `chrono`, `--all-features`).
  The configurations ran interleaved, A B C D A B C D A, with every build
  compiled first. The three A runs agree within 1% on every AES row.

## 2. Which commit

Between 0.9.2 and 0.9.3 the aarch64 backend changed in one commit. The
microbenchmark built against block-ciphers checkouts:

| commit | one block | chain, per block | 32 blocks | 256 blocks |
|---|---|---|---|---|
| `aes-v0.9.2` | 6.5 | 4.9 | 19.6 | 156 |
| parent of #580 | 6.5 | 4.9 | 19.8 | 161 |
| **#580** 9b8b0c9 "enable VAES backends by default, bump MSRV to 1.89" | 9.3 | 9.1 | 49.8 | 387 |
| parent of #598 | 9.0 | 9.1 | 49.8 | 386 |
| **#598** a7136b4 "add `#[inline]` attributes" | 7.2 | 4.9 | 20.2 | 162 |
| master b99ebe6 | 6.5 | 4.9 | 20.3 | 161 |

#580 moved the aarch64 loads and stores into new helpers in
`backends/aarch64_aes/utils.rs`:

```rust
#[target_feature(enable = "neon")]
pub(super) fn load_block(block: &Block) -> uint8x16_t { /* vld1q_u8 */ }
```

They have no `#[inline]`, and that hurts here for three reasons:

- **They can't be inlined across crates.** Without the attribute, rustc
  only makes a function inlinable in other crates if it calls nothing.
  These helpers call `vld1q_u8`, `vst1q_u8` and `as_ptr`, so they don't
  qualify (rustc `cross_crate_inline.rs`: `checker.calls == 0`).
- **Our crate makes the call.** The generic `encrypt<RK>` and
  `batch_encrypt` are instantiated in the calling crate, so every block
  load and store becomes a real call into `aes`.
- **Every call on aarch64 is expensive.** The calling convention
  preserves only the low 64 bits of v8–v15, so each call forces the
  128-bit round keys and block state out to the stack and back. That
  matches the 99 loads, 40 stores and 34 calls in the earlier disassembly.

Inside the `aes` crate the helpers inline as normal, so upstream's own
benches would not have caught it.

#598 adds `#[inline]` to the helpers. Its description: "Perf was ~1.5-2x
worse after updating aes from 0.9.2 to 0.9.3 and turned out it was due to
some functions not getting inlined across crate boundaries." It is on
master but not in a release; crates.io's latest is still 0.9.3.

## 3. The comparison cost: zeroize on drop

The legacy comparator (`compare_raw_slices` and `Ord`) builds an
`Aes128Z2Hash`, which means a fresh `Aes128` keyed by the ciphertext nonce,
on every call, and drops it afterwards. The drop changed in 0.9.0:

- **0.8.4** drops only the active backend's round keys.
- **0.9.x** calls `zeroize::zeroize_flat_type(self)` over the whole struct.
  The struct is a union of the hardware and software backends, so it's as
  large as the software key schedule.

`zeroize_flat_type` writes one byte at a time with `write_volatile`, which
the compiler can't widen. That's about one byte per cycle.

Microbenchmark, ns, with the `zeroize` feature as ore-rs enables it:

| `aes` | `size_of::<Aes128>()` | key schedule + drop | new + 1 block + drop | `Aes128Enc` new + 1 block + drop (size) |
|---|---|---|---|---|
| 0.8.4 + `aes_armv8` | 704 B | 61 | 47 | 45 (704 B) |
| 0.9.2 | 704 B | 209 | 208 | — |
| 0.9.3 | 704 B | 210 | 217 | 215 (704 B) |
| master | 352 B | 125 | 125 | 80 (176 B) |

Without the `zeroize` feature, the same key schedule takes 39 ns on every
0.9 release. Upstream #594 (after 0.9.3) shrank the software round keys,
which halves the struct on master.

The extra drop cost accounts for the comparison slowdowns. For
`compare-4`, master is 64 ns slower than 0.8 in the microbenchmark and
65 ns slower in the ore-rs bench; for 0.9.2 the figures are 148 ns and
150 ns.

Upstream: in RustCrypto/utils#1504 (a zeroize 1.9 regression, closed
2026-09-11), a maintainer noted that `zeroize_flat_type` "currently
zeroizes data byte-by-byte. Considering that it can be used on somewhat
large types, this is far from ideal". Nothing has changed since.

## 5. Mitigation: `Aes128Enc`

ore-rs only ever encrypts with AES, in the PRF, PRNG, hash and CMAC. A
prototype replaced `aes::Aes128` with the encrypt-only `aes::Aes128Enc` in
those four files. Every test, including the pinned ciphertext vectors,
passed unchanged. It ran as interleaved A E C F A E C F:

| bench | A: 0.8.4 | E: 0.8.4 + `Aes128Enc` | C: master | F: master + `Aes128Enc` |
|---|---|---|---|---|
| compare-4 | 161 ns | −19% | +40% | +11% |
| compare-8 | 233 ns | −20% | +21% | +1% |
| compare-date | 141 ns | −8% | +60% | +27% |
| compare-datetime | 257 ns | −5% | +33% | +14% |
| compare-decimal | 282 ns | −4% | +31% | +15% |
| encrypt-8 | 17.76 µs | −3% | −8% | −10% |
| encrypt-left-8 | 12.95 µs | −6% | −12% | −15% |
| encrypt-decimal | 29.51 µs | −0% | −5% | −9% |
| chained-encrypt-str-17 | 13.92 µs | −1% | −4% | −5% |

The swap is worth doing on 0.8 too: it skips the decryption key schedule
nobody uses. On master, the comparisons left over are still paying the
byte-wise wipe of 176 bytes.

**Anomaly, not AES:** `compare-decimal-slice` is 286 ns on A but 415–511 ns
on E, C and F, both runs. In exactly those three binaries, LLVM inlines
`compare_raw_slices` into the decimal bench; in A it stays a separate
function. The other slice benches keep it out of line and track their
non-slice rows. So it's a code-generation artifact of that bench, not an
AES cost.

## What this means for #106

- **Releases.** Do not ship on 0.9.3. Either 0.9.2 or the next release with
  #598 fixes encryption.
- **0.9.2.** Not a good pin: its legacy comparisons are 60–120% slower
  (the 704-byte wipe), and Bit6 encryption is 16–23% slower.
- **The next release.** Any release with #598 and #594 does better than 0.8
  on every encryption. Its legacy comparisons are 21–62% slower, or 1–29%
  with `Aes128Enc`.
- **Full parity on comparisons** needs `zeroize_flat_type` to wipe in wider
  words. That's an upstream change in `zeroize`.
- **`Aes128Enc` stands on its own.** It's worth taking separately, on 0.8,
  for a 5–20% faster legacy compare.

None of this was measured on x86_64. #598 changes the x86 helpers too.
