# `aes` 0.8 vs 0.9 on aarch64

#86 proposed upgrading `aes` from 0.8.4 to 0.9 to drop the `--cfg aes_armv8`
workaround: 0.9 turns the ARMv8 backend on by default. PR #106 did the
upgrade. Every ciphertext was unchanged, but ore-rs got much slower on
aarch64. This note records the measurements behind keeping 0.8 (#106 is
parked as a draft).

**Result:** on an Apple M4, `aes` 0.9.3 takes 2x as long per single-block call
and 2.4x as long per bulk call as 0.8.4 with `aes_armv8`. Full encryption
gets 32–52% slower, chained encryption about 3x slower, and comparisons
59–123% slower.

## Machine and method

- Apple M4 (4 performance, 6 efficiency cores), macOS, on mains power with
  Low Power Mode off; rustc 1.89.0 for both sides, `cargo bench` release
  profile, criterion 0.5 medians.
- **A:** `main` at f72d7a5 (`aes` 0.8.4 with `--cfg aes_armv8` from
  `.cargo/config.toml`). **B:** `chore/aes-0.9` at 528fca7 (`aes` 0.9.3,
  no rustflags). No `RUSTFLAGS` was set in the environment.
- The order was A, B, A. Both builds were compiled before any
  measurement. The two A runs agree within 1.2% on every row except
  `serialize-decimal` (3.6%), so drift is far smaller than the effect.
- The whole sequence was run twice. The first run had a busy machine and
  more drift (up to 12.8%), but its B-vs-A changes match the quiet run's
  within a few points, except `compare-4` (+250% then, +94% here). The
  tables below are from the quiet run.
- Benches: `oreaes128`, `bit6`, `chained`, `decimal`, `chrono`, all with
  `--all-features`.

The pattern follows how each path calls AES:

- **Chained encryption**, which suffers most, runs a CMAC chain of
  single-block calls for every prefix.
- **Legacy comparisons** hash with single-block calls.
- **Full encryption** of the fixed schemes is dominated by bulk calls over 64
  or 256 blocks.
- **Left-only encryption** of the legacy scheme is dominated by work that
  isn't AES, and barely moves.

## 2. AES alone

A standalone crate (not in this repository) linked `aes` 0.8.4 and 0.9.3
into one binary, plus `aws-lc-sys` 0.45 and `aws-lc-rs` 1.18.1. A test checked
that every backend gives identical output and matches the FIPS-197 C.1
vector. The aarch64 rustflags carried `--cfg aes_armv8`, which only 0.8
reads. Criterion defaults; medians:

| shape | aes 0.8.4 + flag | aes 0.9.3 | aws-lc-sys `AES_encrypt` | aws-lc-sys EVP ECB, no padding | aws-lc-rs streaming ECB |
|---|---|---|---|---|---|
| one block, fixed key | 5.8 ns | 11.6 ns | 7.8 ns | 8.3 ns | 40.1 ns |
| key schedule | 38.2 ns | 37.7 ns | 15.9 ns | — | — |
| 32 blocks, fixed key | 20.7 ns | 50.8 ns | 75.5 ns | 56.3 ns | 91.0 ns |
| 64 blocks, fixed key | 41.7 ns | 101.8 ns | 147.8 ns | 103.5 ns | 142.8 ns |
| 256 blocks, fixed key | 164 ns | 399 ns | 586 ns | 396 ns | 456 ns |
| new key + 32 blocks | 61.8 ns | 89.3 ns | 82.9 ns | 90.4 ns (reused context) | 172.9 ns |

`aws-lc-rs` `PaddedBlockEncryptingKey::ecb_pkcs7` took 380 ns for new key +
32 blocks; it allocates and always adds a padding block.

The key schedule costs the same in both `aes` versions; only the block
calls slowed down. Another run with `-C target-feature=+aes` changed nothing:
`aarch64-apple-darwin` already enables `aes`, so this is not the
target-feature inlining problem behind RustCrypto/block-ciphers#484 and
#574. In the disassembly, 0.9.3's bulk path has about 99 128-bit
loads, 40 stores and 34 calls, against 0.8.4's 13, 7 and 5. The AES state
goes through memory, and helper calls are not inlined. AESE/AESMC pairing is
the same in both (about 90% adjacent), so instruction fusion is not the
cause.

## 3. aws-lc as an alternative

`aws-lc-rs` has no raw block-cipher API. Its only public ECB is
PKCS#7-padded (`PaddedBlockEncryptingKey::ecb_pkcs7`,
`StreamingEncryptingKey::ecb_pkcs7`), and its single-block `encrypt_block`
is `pub(crate)`. Raw access means `aws-lc-sys` FFI. Even then, it beats
`aes` 0.8 only in the key schedule (2.4x faster). That doesn't make up
for slower block calls in any shape ore-rs uses, and it would add a C build
dependency. Not pursued.

## 4. Upstream status (2026-10-12)

- **RustCrypto/block-ciphers#574** (x86_64, 0.8 → 0.9.1 regression): fixed
  by #575 ("aes: refactor backends"), released in 0.9.2. That refactor also
  reworked the aarch64 backend, but 0.9.3 is still slow on aarch64.
- **#484** (aarch64 runtime-detection overhead, 2025) and **#513** (slow AES
  on Apple Silicon, 2025): closed. Both came down to per-call dispatch or
  key-schedule cost, which doesn't fit here: the key schedule is unchanged,
  and `+aes` doesn't help.
- No open issue reports the aarch64 slowdown in 0.9.2 or 0.9.3.

## Decision

Stay on `aes` 0.8.4 with `--cfg aes_armv8`. Make the silent fallback from
#86 detectable instead: `ore_rs::hardware_aes()`, and a test that fails on
an AES-capable aarch64 host when the flag is missing. Revisit #106 when
upstream fixes the aarch64 path, using the microbenchmark above to check.
